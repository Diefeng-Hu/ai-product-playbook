# 案例：增量镜像是持续对账

> **案例库 · 数据管线**
>
> 撰写日期：2026-07-13，精简日期：2026-08-31

## 背景

把本地文件、开放 API 和没有稳定 API 的第三方数据镜像到统一语料库。一次抓取很容易，长期保持副本与事实源一致才是困难部分。

## 提炼出的判断

镜像管线至少需要四个机制：

| 机制 | 解决的问题 |
| --- | --- |
| 断点续传 | 中断后不必从头开始 |
| 去重 | 多次导出或续写不会重复加权 |
| 删除传播 | 源端删除后副本不继续引用旧内容 |
| 缺失清单 | 无法同步的来源被显式看见 |

能无人值守同步的来源与必须人工导出的来源应分层处理。人工步骤本身不是失败，但必须明确频率、落盘位置和后续接管流程，不能让最脆弱的数据源拖垮整条管线。

## 为什么降为案例

具体平台的反爬、下载和浏览器实现会快速变化。长期值得保留的是“镜像必须持续对账、缺失必须可见”，而不是某次抓取技巧。
